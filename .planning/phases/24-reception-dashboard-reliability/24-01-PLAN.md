# Phase 24 — Reception Dashboard Reliability Plan

> **For agentic workers:** Execute one task owner at a time for shared dashboard/query/API files. Keep discovery agents read-only. Follow `AGENTS.md` and the phase design.

**Goal:** Make dashboard figures dependable and reception actions faster to use while preserving existing OPD and financial rules.

**Architecture:** Keep the existing React Query, FastAPI and PostgreSQL architecture. Make query freshness explicit, use backend-defined reporting and department values, then make small, evidence-backed interaction changes. Coordinate shared API changes instead of inferring missing business rules in the UI.

**Tech Stack:** React, TypeScript, TanStack Query, FastAPI, SQLAlchemy, PostgreSQL, Vitest, pytest.

**Spec:** `.planning/phases/24-reception-dashboard-reliability/24-DESIGN.md`

## Global Constraints

- Preserve the existing frontend, backend and database architecture.
- The app must continue to work offline on the hospital LAN.
- Reception owns routine payment collection; payment history is never overwritten.
- Queue entries remain linked to their correct visit and doctor.
- Never invent a net collection policy or a department membership.
- Use synthetic data only; never reset production data or delete historical records.
- Backend authorization remains mandatory; never weaken permissions.
- Before each repair batch, create a Git checkpoint and inspect current dirty files.
- Do not claim verification that has not been run; incomplete verification is `IMPLEMENTED — NOT VERIFIED`.

## Review Focus

- Overview refresh failure while cached values exist: show the last successful refresh and a stale/error indicator, not a current zero.
- Concurrent workstation queue updates: preserve polling and optimistic-concurrency conflict behavior.
- Reversal recorded today for a payment from an earlier date: show activity buckets separately; do not silently net.
- Doctor assigned to multiple departments: do not derive a single service department from qualification.
- Delayed patient filtered while another doctor/status filter is active: keep the alert's queue target unambiguous and reversible.
- Text resizing, keyboard-only operation, screen-reader updates, contrast, and small viewports: preserve all queue actions and context.

## Checkpoint and integration protocol

Before each repair batch, inspect `git status --short` and create a checkpoint according to repository workflow. The current OPD edits overlap the ownership set above and must be reconciled first. Do not run parallel implementation on dashboard, query or overview API files. After each task, a separate reviewer checks the diff and test evidence before the next dependent task begins.

## Release criteria

The feature is not VERIFIED until frontend interaction, API behavior, database persistence (where relevant), related modules, authorization, reload persistence, regression tests, and receptionist walkthrough evidence are recorded. If staff walkthrough is unavailable, technical changes may be implemented but satisfaction remains unverified.
