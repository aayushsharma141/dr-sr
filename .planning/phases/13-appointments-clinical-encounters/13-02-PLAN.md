# Plan 13-02: Daily Token Service & Appointment Booking REST Endpoints

## Purpose
Implement atomic per-doctor daily token generation with concurrent safety and the reception appointment booking API endpoints (`POST /api/appointments`, `GET /api/appointments`).

## Requirements Covered
- `APT-01`: Reception books a per-doctor daily appointment with a token number unique per doctor per day.

## Proposed Changes

### 1. `backend/src/kalyan_api/services/token_service.py`
- Function `generate_next_daily_token(session: Session, doctor_id: int, appointment_date: date) -> int`:
  - Acquires row lock using `SELECT last_token FROM daily_token_sequences WHERE doctor_id = :doctor_id AND appointment_date = :appointment_date FOR UPDATE`.
  - Upserts counter row if missing.
  - Returns `next_token = last_token + 1` and updates sequence record atomically.

### 2. `backend/src/kalyan_api/schemas/appointment.py`
- Pydantic schemas:
  - `AppointmentCreate`: `patient_id: int`, `doctor_id: int`, `appointment_date: date`, `notes: str | None`
  - `AppointmentRead`: full appointment payload including token number, doctor details, patient URN and name.
  - `AppointmentListResponse`: pagination & list wrapper.

### 3. `backend/src/kalyan_api/routers/appointments.py`
- `POST /api/appointments`:
  - Requires `APPOINTMENT_WRITE` permission (Reception & Doctor).
  - Validates active patient exists and active doctor exists.
  - Allocates token atomically via `token_service`.
  - Creates appointment in `BOOKED` status.
  - Records audit row: `action="appointment.created"`.
- `GET /api/appointments`:
  - Requires `APPOINTMENT_READ` permission.
  - Query parameters: `doctor_id: int | None`, `date: date | None`, `status: str | None`, `patient_id: int | None`.
  - When invoked by Doctor, scoped by default to their `principal.doctor_id`.

### 4. Integration Test
- `backend/tests/test_token_concurrency.py`:
  - 20 parallel threads booking appointments concurrently for the same doctor on the same date.
  - Asserts strictly 20 unique tokens with zero duplicates and zero gaps (tokens 1 through 20).

## Verification
- Concurrency test passes with 20 threads.
- Unit tests verify booking validation (inactive doctor rejected, nonexistent patient rejected).
