<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| File Upload -> Server Memory / Staging | Untrusted bulk spreadsheet files cross boundary; staging table isolates unvalidated rows from production patient table |
| Staging Table -> Production Patients Table | Only validated, duplicate-resolved rows cross into `patients` during the atomic commit transaction |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-20-13 | Tampering / Integrity | `backend/src/kalyan_api/services/import_service.py` | high | mitigate | Strictly forbid updating or overwriting existing patient records. Duplicate candidates can only be skipped or imported as new records with distinct URNs (D-20-13). |
| T-20-14 | Information Integrity | `backend/src/kalyan_api/services/urn_service.py` | high | mitigate | Allocate URNs exclusively inside the commit transaction for rows that successfully insert. Staging rows and invalid rows never touch `urn_service`, ensuring zero URN gaps (D-20-09, D-20-11). |
| T-20-15 | Denial of Service / Data Loss | `backend/src/kalyan_api/routers/imports.py` | high | mitigate | Enforce automatic safety backup before committing rows. If backup fails, abort the commit with HTTP 500 / 422 and rollback transaction (D-20-12). |
| T-20-SC | Tampering | npm/pip/cargo installs | high | mitigate | `openpyxl` wheel installation verified against standard wheel format; pure Python dependency. |
</threat_model>

    3. In `backend/src/kalyan_api/services/import_service.py`:
       - Implement spreadsheet parsing supporting CSV (detecting UTF-8, UTF-8-BOM, Windows-1252) and XLSX (using `openpyxl`).
       - `inspect_file(file_bytes, filename) -> dict`: returns encoding, delimiter, total row count, header preview, sample rows.
       - `stage_batch(session, user_id, filename, file_bytes, mapping) -> PatientImportBatch`: creates batch and staging rows.
       - `validate_batch(session, batch_id) -> dict`:
         - Enforces required fields: `full_name` (min 2), `guardian_name` (min 2), `gender` ('M'/'F'/'O'), `age_years` (0-150), `mobile` (10 digits), `address`. Missing fields flag row as `INVALID` with specific field errors.
         - Duplicate candidate matching: matches against `Patient` table by exact `mobile` AND `address`, OR exact `legacy_urn`, OR exact `mobile` and similar `full_name`. Sets row status to `DUPLICATE` and links `duplicate_patient_id`.
       - `resolve_duplicate(session, batch_id, row_id, resolution)`: records `SKIP` or `IMPORT_AS_NEW`.
       - `commit_batch(session, user_id, batch_id, cfg) -> dict`:
         - Step 1: Run pre-commit backup via `backup_service.create_backup_bundle(session, cfg, user_id)`. If it raises an exception, abort commit immediately (D-20-12).
         - Step 2: Iterate over staging rows where `validation_status == 'VALID'` or (`validation_status == 'DUPLICATE'` and `duplicate_resolution == 'IMPORT_AS_NEW'`).
         - Step 3: For each row, call `urn_service.allocate_next_urn(session)`.
         - Step 4: Insert new `Patient` record with the allocated URN and `legacy_urn`. Record `allocated_urn` on staging row.
         - Step 5: Mark batch as `COMMITTED`, record commit timestamp and counts.
       - `export_error_records_csv(session, batch_id) -> str`: generates CSV of invalid or skipped rows with reasons for admin offline review.
    4. Write comprehensive tests in `backend/tests/test_patient_import_service.py`.
