# The synthetic dataset — and how to get rid of it

The hospital asked for a system that is demonstrated with **synthetic test data only, with no
real patient information anywhere**. This document explains exactly what that data is, what the
system does to keep it obvious, and the two ways of moving to real patients.

---

## 1. What "synthetic" means here

Every record in the demo database was generated by `scripts/seed.js` from fixed name lists,
arithmetic date offsets and random-but-deterministic choices. No row was copied from a real
person, a real hospital system, a public dataset or the internet.

* Names are common Indian given names and surnames combined mechanically (`Ajay Mhatre`,
  `Madhuri More`); the combinations are not real people at Kalyan Hospital.
* Phone numbers are in the visible test range / obviously fake patterns, not scraped numbers.
* Clinical text is composed from a small set of generic complaints and findings
  ("Low back pain radiating to left leg", "Blurred vision for distance"), split between
  the Physiotherapy and Ophthalmology departments.
* Uploaded documents are PDFs **generated in code** that say, on the page:
  *"SYNTHETIC DEMO DOCUMENT — It contains no real clinical information."*
* Settings carry the hospital address used by the v3 app; phone, e-mail and registration
  number are left blank until the hospital supplies them.

## 2. How the system keeps synthetic data obvious

* **Dashboard banner:** a permanent amber strip — *"This installation is running on synthetic
  test data. No real patient information is stored."*
* **Settings → Dataset:** the state is shown as *Synthetic test data* with an explicit tick box.
* **Backups & system:** the *Dataset* row shows a `Synthetic test data` pill next to the record
  counts, alongside every backup you take.
* **Receipts and prescriptions** generated in the demo carry the disclaimer
  *"Synthetic demonstration record — not a real patient document."*
* **Documents** state their synthetic nature inside the file itself.
* **Seed output** ends with a boxed warning telling whoever ran it to change passwords and clear
  the dataset before real use.
* **Settings → Dataset warning** appears in amber whenever the flag is on, so the laboratory
  state cannot be mistaken for live data by someone joining later.

Nothing in the seed can overwrite real data by accident: `npm run seed` **refuses to run at all**
when the database already contains patient records, and `npm run seed:reset` (which passes
`--reset --yes`) asks for confirmation and prints the record counts it is about to delete.

---

## 3. Where the data is kept

| Item | Location |
|---|---|
| Database | `data/kalyan.db` (plus `-wal`, `-shm` while running) |
| Generated documents | `data/uploads/*.khc` (encrypted) |
| Backup taken by the seed | `data/backups/kalyan-*.khb` |
| Encryption keys | `data/keys/*.key` |
| Logs | `data/logs/` |

There is no other copy. Nothing is written outside the application folder, no network calls are
made, and no data leaves the machine.

## 4. Option A (recommended): start the real installation clean

Use this when the clinic is about to go live. It takes five minutes and leaves no trace of the
demo.

```bat
:: 1. Stop the server (Ctrl+C in the server window), then:
rmdir /s /q data            :: Windows   (Linux/macOS: rm -rf data)

:: 2. Start again — this is a brand-new installation
npm start
```

The first start prints a **one-time setup code** on the console. Open `http://localhost:3000/setup`
on the server PC, enter the code, and create the real first administrator. Then:

1. **Settings** → real hospital name, address, phone, registration, disclaimer.
2. **Staff accounts** → one account per person (Administrator, Doctor, Nurse, Reception).
   Do not recreate `admin`, `dr.verma` or `reception` as shared logins.
3. **Settings → Dataset** → the tick box is already off (a fresh database has no synthetic
   flag), verify it reads *"This installation contains live clinic data."*
4. **Backups & system → Back up now**, then export one copy off-site.
5. Register the first real patient and print a test receipt.

Everything is now empty and real: no demo patients, no demo invoices, no demo staff, number
sequences starting at `KH-000001`.

> Prefer to keep the demo running on a *separate* PC for training staff? Do that on a second
> machine (copy the folder, run `npm run seed`) and keep the real server clean. Two servers on
> one LAN is fine as long as staff use the right address — or simply train before go-live.

## 5. Option B: keep a training installation, and reset it when it gets messy

If the demo data is genuinely useful — for training new reception staff, or for showing the
system to a doctor — run it on a **separate** installation and keep the live server clean:

```bat
:: on the training PC only
npm run seed:reset
```

`seed:reset` wipes that database and reloads a fresh synthetic dataset (it asks for confirmation
and prints the record counts it is about to delete). Use it whenever the training data becomes
chaotic. Never run it on the live server.

**There is deliberately no "delete the demo patients" button.** Removing only part of a medical
database leaves dangling references, half-used number sequences and an audit trail that points at
records that no longer exist — much worse than starting clean. The supported way to go from
synthetic to live is Option A: a fresh `data` folder, a fresh setup code, real accounts.

If you want to keep the hospital settings and staff accounts you already typed in, note them
before the reset and retype them afterwards: **Settings** and **Staff accounts** together are a
five-minute job for a clinic with five staff, and it removes every trace of the demo.

## 6. Housekeeping rules for synthetic data

* Never type a real patient into a demo installation. If someone does, treat it as a privacy
  incident: delete the installation's `data` folder and note it.
* Never copy a production `data` folder to a demo PC, and never restore a demo backup over live
  data (`npm run restore` asks you to type `restore`, and the manifest shows the record counts —
  read them).
* The demo password is public knowledge. A server still reachable from the LAN with
  `Kalyan#Clinic2026` accounts is an open door: disable the demo accounts the moment the clinic
  uses the system.
* Off-site backups of a demo installation contain nothing sensitive, but keep treating the
  habit the same way so the real routine is not weakened.
