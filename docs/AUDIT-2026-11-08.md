## 1.2 Findings

### F-1 (High) Plain HTTP; session cookie and PHI travel in clear on the LAN
`config.py` `cookie_secure = False`; CSP has no TLS posture; Phase 18 notes "HTTPS decision still open". Anyone on the LAN segment can sniff the session cookie and CSRF token (both are in the same response/headers path) and read patient data. DEPLOYMENT.md itself says an HTTP exception needs *written client approval*.
**Fix:** decide HTTPS now (self-signed/internal CA via a reverse proxy such as Caddy/IIS ARR is feasible offline) and set `cookie_secure=True`; otherwise record the signed exception and isolate the clinic VLAN.

### F-2 (Medium) Restore feeds archive SQL to `psql` as DB owner, with a self-attested integrity check
`services/backup_service.py` `restore_database_sql` / `verify_backup_bundle`:
- The SHA-256 lives in the **same archive** as the data (`manifest.json`). It catches corruption, not tampering.
- `psql -f db.sql` is run as `kalyan_owner`. psql meta-commands (`\!`, `\copy … PROGRAM`, `\i`) in a crafted `db.sql` are not filtered, so a forged bundle placed in `backup_dir` runs commands as the service account.
- Prerequisite: write access to `backup_dir` (the API can only restore files already in that directory; `resolve_archive_in_dir` is traversal-safe). Realistic threat = someone with file access to the backup drive, or a stolen/swapped drive.
**Fix:** reject any dump line beginning with `\` before running psql (cheap, ~10 lines); sign the manifest with an HMAC keyed from a server-side secret; consider `pg_restore` with custom format.

### F-3 (High, process) Branch is red: 7 deterministic + 3 load-flaky frontend test failures
- 7 deterministic: `admin-navigation-architecture.test.tsx` (6) and `app-shell.test.tsx` (1) — uncommitted test edits expect the new 5-section registry (`'overview'` section, `hospital-configuration` id, `/admin` route shape) that the committed `modules.ts` / working-tree `AppShell.tsx` don't yet satisfy. This is Phase 20 plan 20-02 in flight, not a regression in shipped code.
- 3 flaky under full-suite load: `settings.test.tsx`, `prescription-workspace.test.tsx`, `treatment-plan-workspace.test.tsx` all **pass when run alone (13/13)**; they time out at 3–4 s inside a 120 s run where jsdom is created 47× (594 s cumulative).
**Fix:** finish 20-02 and get the 7 green before committing; raise per-test timeout or set `pool: 'vmThreads'` / shared jsdom (vitest's own hint) to kill the flakes. CI runs `npm run test`, so this would fail the frontend job.

### F-4 (Medium) Backups are unencrypted PHI
Plain `.tar.gz` of the full SQL dump + all patient photos, copied to a "second drive" (and "approved destinations"). A lost/stolen drive is a full patient-data breach.
**Fix:** encrypt at rest (e.g. age/7-zip AES with a passphrase held by the admin) or require BitLocker on the target volume and record that as an acceptance gate.

### F-5 (Medium) Installer and runbook don't match each other or the code
- `deploy/install.ps1` declares `-DbAppPassword` / `-DbOwnerPassword` but **never uses them**; it doesn't create roles/DB, write `backend/.env`, set a firewall rule, or build the frontend. It just venv + `pip install -e` + migrate.
- `DEPLOYMENT.md` still says "Target runbook; deployment not yet tested… exact commands to be added".
- `ARCHITECTURE.md`, `TASKS.md`, `TEST_PLAN.md`, `SECURITY.md` all say "not implemented / evidence pending" while STATE.md reports phases 11–17 and 19 complete.
**Fix:** either wire the params into role/DB/.env creation or delete them; refresh the five top-level docs' status lines; add the firewall rule (`New-NetFirewallRule`, LAN subnet only) to the script.

### F-6 (Medium, governance) Planning state has drifted from reality
- `REQUIREMENTS.md`: **10 checked / 49 unchecked** and every traceability row is "Pending", despite 8 of 10 phases complete.
- ROADMAP: Phase 18 plans 06–08 open; **criterion 4 unmet** (36 existing violations "capped" via a TODO(18) allow-list in `src/test/guards/guards.test.ts`); manual accessibility checks outstanding; physical printer test **waived** (PRN-01 requires verification on the actual printer).
- STATE.md front-matter says `status: executing` but `active_phase: null`.
**Fix:** run the requirements traceability sweep; get the printer waiver and criterion-4 exception into the client acceptance record.

### F-7 (Low) Lockout can be used to deny service
5 bad passwords lock an account 15 min (`lockout_threshold`), per account, from any LAN PC. A bored user can keep the only admin locked out. Per-IP throttle (20 / 15 min) doesn't stop it.
**Fix:** keep the console break-glass reset (exists per `test_cli_admin.py`), document it; optionally don't lock ADMIN accounts from the console's own IP.

### F-8 (Low) Photo upload validation
`photo_service.validate_photo_bytes`: magic-byte only (JPEG/PNG), no decode/re-encode, validated after the whole body is read into memory (limit 5 MB, so bounded). Content is served from the same origin, but `X-Content-Type-Options: nosniff` + CSP `default-src 'self'` are set, so risk is low.
**Fix (optional):** decode with Pillow and re-encode to strip polyglots/EXIF GPS.

### F-9 (Low) Timing oracle dummy hash uses fixed Argon2 params
`core/security.py` `_DUMMY_HASH` is `m=65536,t=3,p=4`; if the admin changes `argon2_*` settings the unknown-user path no longer takes the same time as the real path.
**Fix:** derive the dummy hash from `build_hasher(settings)` at startup.

### F-10 (Low) Maintainability hot-spots
`routers/areas.py` 1010 lines (dashboard aggregation logic inside a router), `ClinicalEncounterWorkspace.tsx` 1483, `api/queries.ts` 1405, `api/types.ts` 1307 (hand-written although an OpenAPI snapshot exists), `ReceptionDashboard.tsx` 1091.
**Fix:** move aggregation into services; generate `types.ts` from the snapshot; split the encounter workspace.

### F-11 (Low) Dependency pinning
Everything pinned except `python-multipart>=0.0.20`. A `requirements.lock.txt` exists, so impact is small; pin it for the offline wheelhouse.

### F-12 (Info / decision) Doctor visibility policy
Roles in code: Doctor has `PATIENT_READ` but **no** `PHOTO_READ`; clinical records are silo'd per doctor (D-03). Your memory notes say "read-all, edit-own" for the 3 doctors is pending sign-off and would reverse locked EG-6. Not a defect — flag so the matrix and SECURITY.md are updated together once decided.

## 1.3 What is solid (keep)
- Default-deny route policy, enforced by test; permissions resolved server-side every request (`current_principal` → `require()`).
- Session tokens stored as SHA-256; 256-bit random; idle (30 m) + absolute (12 h) expiry; revocation checked each request; rotation on login.
- CSRF: global `verify_origin` + per-session `X-CSRF-Token` with `hmac.compare_digest`.
- Argon2id; generic login error (no user enumeration); DB-backed per-IP throttle with atomic upsert.
- Client IP taken from the TCP peer only (no spoofable `X-Forwarded-For`).
- `/docs`, `/redoc`, `/openapi.json` disabled; `no-store` on `/api`; security headers set.
- Backup verify-before-restore, mandatory pre-restore snapshot, single-transaction restore with `ON_ERROR_STOP`, tar `filter="data"`, destination-dir allow-list (UNC refused).
- Append-only audit, DB triggers on clinical notes/sessions, integer paise, optimistic locking with 409, setup-code flow with one-time hash.

# PART 2 — Legacy v2.0 desktop app (PySide6 + SQLite)

Scope: `legacy/app/` (≈9.4k LOC), `legacy/main.py`, `legacy/tests/` (19 files), `legacy/build_exe.bat`, `legacy/data/`. Last changed 2026-10-30; project docs declare it **reference-only** and "must not be mixed" with v3. The findings matter only if it is, or might again be, run against real patients (PROJECT.md says it stays valid for a single-PC deployment).

## 2.1 Findings

### L-1 (Critical, if ever deployed) Hard-coded default administrator `admin` / `kalyan@admin`
`legacy/app/services/auth_service.py:20-25` — `AuthService.__init__(auto_seed_demo=True)` calls `ensure_default_admin()` which creates `admin`/`kalyan@admin` whenever no admin exists. The production code path (`backup_view.py:35`) constructs `AuthService(db_path=…)` with the default, and `setup_initial_admin()` (the proper first-run path) has **no caller**. So every fresh install ships a known credential that gates restore and demo-reset. The local `legacy/data/kalyan.db` currently contains an `admin` user (I did not test whether it still has the default password).
**Fix:** default `auto_seed_demo=False`; wire `setup_initial_admin` into first launch; only tests opt in.

### L-2 (High) No application login at all
`legacy/main.py` → `MainWindow` directly; the only auth gate is `AdminAuthDialog` before **restore** and **demo reset**. Everything else (patient data, payments, prescriptions) is open to whoever has the PC session. Roles in the `users` table are effectively unused.

### L-3 (High) No brute-force protection
`authenticate()` has no lockout/throttle; failures are only logged. Attackable via the restore dialog.

### L-4 (Medium) Weak password hashing parameters
PBKDF2-HMAC-SHA256 at **100,000** iterations (`ITERATIONS`); current OWASP guidance is ≥600,000 (or Argon2id). Per-user random salt and `hmac.compare_digest` are correct.

### L-5 (Medium) Audit log is not tamper-evident
Docstring says "immutable / tamper-evident", but `legacy/app/db/schema.sql` has **0 triggers**: rows can be UPDATEd/DELETEd by anyone with the DB file. v3 enforces this in Postgres. No immutability triggers on treatment sessions or payments either.

### L-6 (Medium) Unsafe data migration backfill
`db/connection.py:_migrate` assigns legacy patients to doctors by `((id-1) % 2) + 1` when `doctor_id IS NULL` — an arbitrary attribution, not real data. Harmless for demo data; wrong for any real legacy migration (MIGRATION.md should not reuse it).

### L-7 (Low) Backup bundles unencrypted, restore overwrites live DB via SQLite `.backup`
Pre-restore safety snapshot + rollback + post-verify exist (good). Photos restore has a traversal guard (`Path(member).name`). `_rollback` uses `zipfile.extractall` on its own snapshot only. Same unencrypted-PHI caveat as F-4.

### L-8 (Low) F-string SQL
Present at `legacy/app/db/connection.py:49,51`, `patient_repository.py:258`, `treatment_repository.py:105`, `backup_service.py:196` — all interpolate **internal constants/fixed clause lists**, user values stay parameterised (`?`). No injection found; flagged so it stays that way.

### L-9 (Low) CI and tooling drift
Legacy CI job uses Python 3.11 while v3 requires ≥3.12 and local venv is 3.12; `.venv` interpreters are missing (can't run tests locally); `.coverage` is **tracked in git** and changes every run; CI push-branch list references old `ui/…` branches.

### L-10 (Info) Positives
Parameterised queries throughout; integer paise money; foreign keys + WAL on; unit tests for auth, billing, backup, audit, treatment (19 files); synthetic demo data only (5 patients / 7 payments locally).

## 2.2 Legacy recommendation
Treat as frozen. Do **not** deploy against real patients. If a single-PC fallback is ever chosen, L-1, L-2, L-3 and L-5 are blockers. Otherwise keep it as the domain reference and it has now been moved to `legacy/` (2026-11-08) so the repo root no longer mixes both architectures.
